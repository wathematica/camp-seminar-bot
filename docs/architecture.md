# 設計メモ

## 責務

| ファイル | 責務 |
|---|---|
| `gas/onSubmit.gs` | フォーム送信を受け、Webhookでカードを1件投稿 |
| `bot.py` | イベント受信、対象の判定、キュー処理、履歴走査、Discord API操作 |
| `voting.py` | 通信を伴わない集計・カード表示の組み立て |
| `storage.py` | SQLiteに投稿ID・履歴カーソル・Webhook IDを記録 |

## 投稿から更新まで

1. GASは最初の回答を見出しにし、それ以外を埋め込みの項目に変換する。
2. Webhook投稿イベントを受けたBotは、チャンネルIDとWebhook IDが対象と一致するか確認する。
3. 投稿IDを保存し、更新キューへ追加する。
4. 所有Webhookでカードを取得し、投票案内または旧形式の見出しから対象カードと確認する。
5. Bot認証で不足している1️⃣・2️⃣・3️⃣を追加し、志望ごとの投票者を取得する。
6. Botを除外し、ユーザーIDで重複を排除する。第一志望から順に採用する。
7. 色・人数・説明・本文に変更があれば、元のWebhookでカードを編集する。

Webhookから取得するカードにも、接続中のDiscordクライアントの状態を関連付けています。これによりリアクション付きカードの絵文字を正しく解析します。カード本文を読むためのMessage Content Intentは使いません。

## イベントと再確認

キャッシュの有無に左右されないraw reactionイベントを使います。自身のBotのリアクションイベントは無視し、同じ投稿への処理はキュー上でまとめます。処理中に新たな変更が来た場合は次の処理を予約します。

60秒ごとに履歴と既知の投稿を再確認します。再起動中の新規投稿、イベント取りこぼし、リアクション全削除にも対応します。新着履歴は200件ずつ処理し、進行位置を保存します。

API読み取りと書き込みは一度の取引ではありません。投票が集中すると一時的に表示が遅れる場合がありますが、次のイベントや定期確認で再集計します。

## 永続化と障害

保存するのは投稿ID、履歴カーソル、対象Webhook IDです。回答本文と投票者名はデータベースに保存せず、更新時にDiscordから取得します。異なるWebhookの保存データを使おうとすると起動を拒否します。

投稿削除が確認できた場合は監視対象から外します。通信エラー時には待機し、後の定期確認で再試行します。discord.pyのHTTP処理を通じてAPIのレート制限に対応します。

## 制約

- 1プロセスで1つのWebhook・通常テキストチャンネルを扱います。
- 複数プロセスでの同時運用、フォーラム・スレッドには対応していません。
- 定期確認は既知の全投稿を再集計するため、合宿規模の利用を想定しています。
- GASは回答IDで重複送信を抑制しますが、投稿成功直後に保存処理が失敗した場合などの完全な一度だけ配信は保証しません。
- フォーム回答の編集、班をまたぐ順位の整合性チェックは行いません。

## テスト

```sh
.venv/bin/python -m unittest discover -s tests -v
```

通信をモックしたテストと、実ライブラリを使うリアクション解析の回帰テストがあります。実Discordでの受け入れ確認は[セットアップ](setup.md)を参照してください。
